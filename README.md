# day-piece-webview

Embed web content in a [Day](https://daybrite.dev) app. The piece uses the platform's browser
engine and provides one Rust API for navigation, JavaScript evaluation, bundled websites, and
application-provided resources.

## Install

```toml
[dependencies]
day-piece-webview = { git = "https://github.com/daybrite/day-piece-webview.git" }
```

`day build` selects the backend feature and stages native code and browser assets automatically.
You do not need a feature entry for each toolkit in the app's dependency declaration.
This checkout requires Rust 1.89+ and Day 0.4. Keep the CLI, framework, and piece compatible;
use the same Day Git source throughout the dependency graph. See [Cargo.toml](Cargo.toml).

## Choose a content source

| Content | Constructor | Typical use |
|---|---|---|
| A website URL | `web_view(url_signal)` | An embedded browser or hosted application |
| A bundled asset directory | `web_view_inline(res::assets::site)` | Help, charts, an editor, or an animation player |
| Bytes supplied by the app | `web_view_resources(provider, path)` | EPUB chapters, archive entries, or generated reports |

For a bundled site at `resource/assets/site/index.html`:

```rust
use day::prelude::*;
use day_piece_webview::web_view_inline;

// `res` is generated by day::resources!() in the application.
fn help_page() -> impl Piece {
    web_view_inline(res::assets::site).id("help-webview")
}
```

The view fills the available space. HTML can reference its own stylesheets, scripts, images,
and other pages with ordinary relative URLs. Use generated resource constants to open bundled
content; paths *inside* a web document remain document-relative.

A resource provider receives each requested path and returns its MIME type and binary body.
The engine resolves relative references; the app need not rewrite every link, extract an
archive, run a local HTTP server, or send the whole document collection through JavaScript.
The provider is synchronous and buffers each requested resource. On web-dom, its callback
runs on the app's browser thread.

## Renderers

| Target | Renderer |
|---|---|
| macos-appkit, macos-gtk, ios-uikit | WKWebView |
| android-mdc | Android WebView |
| linux-gtk | WebKitGTK 6 |
| macos-qt, linux-qt | Qt WebEngine; requires WebEngine at build time |
| windows-xaml | WebView2 composition controller in the XAML visual tree |
| windows-gtk | WebView2 child window through Wry |
| windows-qt | Qt WebEngine when available; otherwise WebView2 through Wry |
| harmony-arkui | ArkWeb through an ArkTS Web component |
| web-dom | An iframe in the host browser |

`support()`, `inline_support()`, and `eval_support()` describe the compiled backend. They do
not probe engine installation, page readiness, service-worker permissions, or whether a remote
site permits embedding. Browser evaluation requires same-origin content. Browser Back, Forward,
and Stop commands are not implemented. See [platform limitations](docs/platforms.md).

## Run the demo

```sh
cd demo
day launch -p macos-appkit --script dayscript/webview.yaml
```

Choose another target with `-p`, for example `ios-uikit`, `android-mdc`, or `web-dom`.
The [demo source](demo/src/lib.rs) includes a JavaScript console, bundled-site navigation, and
a resource tree with CSS imports, an image, and a nested document.

[Demo website](https://daybrite.github.io/day-piece-webview/) ·
[Browser app](https://daybrite.github.io/day-piece-webview/webapp/) ·
[Platform screenshots](https://daybrite.github.io/day-piece-webview/gallery/)

CI builds and runs the demo on eight primary platform/toolkit pairs. These are execution tests,
not just compile checks. The [CI audit](docs/testing.md#observed-results) records a Linux GTK
resource-loading failure in the first provider run; the other primary targets passed. Configured
coverage should not be mistaken for an entirely passing matrix.

For local framework development, run `day patch --local ../day` from this repository, or
`day patch --local ../../day` from `demo/`. The demo depends on this piece by path.
Run `cargo test` and `node --test tests/*.mjs` at the repository root for host-side tests.
